# 로드맵

AI가 고친 C++ 게임 서버 코드를 **사람이 흐름으로 확인**하는 데 필요한 기능을 단계별로 만든다.
웹 API 개념(라우트, 미들웨어, 컨트롤러)이 아니라 게임 서버 개념(패킷, 프로세스 간 중계, 레인)을 기준으로 한다.
순서는 "AI가 고친 코드를 리뷰한다"는 목적에 가까운 것부터.

## 3단계 — 게임 서버 보기 ✅ 완료

| 보기 | 내용 | 상태 |
|---|---|---|
| 패킷 여정 | 보낸 곳(`SendPacket(PacketId::X)`, 보낸 변수의 타입)과 X 를 받는 곳(핸들러 등록, `case`)을 이름으로 이어 **프로세스를 넘는 흐름**. 중계 봉투를 연 곳(case)부터는 같은 프로세스 안 호출로 잇는다 | ✅ |
| 메시지 연결 | 같은 프로세스 안 메시지(레인: `PushMsg(EMsg::X)` → `Regist(EMsg::X, &C::H)`)를 호출 선으로. 1단계에서 남긴 "레인을 거치는 경로" | ✅ |
| 시작 흐름 | `main` 진입점(프로세스마다 따로) + 흐름 요약: 설정 → 스레드·레인 → 핸들러 등록 → 리스너 순서 | ✅ |
| DB와 캐시 | 흐름 요약의 표시(DB·캐시·작업 단위). 호출로 안 잡히는 SP 이름·`DbCommand{...}` 는 본문 줄 규칙으로 | ✅ |
| 전체 흐름도 | 프로세스(빌드 프로젝트) × 클래스 지도, 클래스 사이 호출, 프로세스를 넘는 패킷. 고른 진입점이 거치는 클래스만 밝게 | ✅ |
| 클래스 다이어그램 | clangd 선언(멤버) + 소스 텍스트(부모)로 UML. 고른 흐름의 클래스 또는 전체 | ✅ |

모두 대상 설정(`channels`, `tags`)으로 바꾸는 범용 규칙이다. 실측은 asio-server(Gateway/World/Zone + 도구 클라이언트),
여러 프로세스·DB 줄·변수 타입 보내기는 `tests/ReviewTool.Tests/Fixtures/multi` 예제로 확인한다.

남은 것: 람다 안의 호출(clangd 가 람다를 따로 본다), 템플릿 생성자 호출처럼 색인이 주지 않는 호출은 여전히 빠진다.

## 4단계 — 점검 규칙 ✅ 완료

게임 서버 규칙을 대상 설정(`targets/*.json` 의 `checks`)으로 켠다. 규칙 엔진은 범용 종류 4가지이고, 이름·파일은 설정으로 맞춘다.

| 점검 | 규칙 종류 | 상태 |
|---|---|---|
| 보상 처리: 재화 차감 → 지급, 되돌리는 호출 없음 | `order` (first → then, unless 없음) | ✅ |
| 모델 변경이 작업 단위(`UnitOfWork`)를 거치지 않는 경로 | `requireWithin` (subject, within) | ✅ |
| 공용 라이브러리가 콘텐츠에 의존 | `dependency` (from → to, 호출과 `#include`) | ✅ |
| 레인 밖에서 게임 상태 접근 | `requireWithin` (withinEdges: Message, withinEntry) | ✅ |
| 락 안에서 I/O | `forbidInScope` (scopeOpen~블록 끝, forbid·forbidTags, 아래 함수까지) | ✅ |
| 근거(파일:줄)·확실도(높음·보통·낮음 + 이유)·꺼진 규칙 "꺼짐"·잘못된 규칙 "오류" | 화면 "점검 규칙", MCP `get_checks`, CLI `check` | ✅ |

점검은 저장된 분석 결과로 그때그때 돈다(규칙을 고쳐도 재분석 없음). 실측은 asio-server(규칙 6개, 잠그는 곳 20곳 확인),
위반이 있는 경우는 `Fixtures/multi` 예제(락 안 Flush, 차감 뒤 지급)를 실제 clangd 로 분석해 확인한다.

## 6단계 — 써 보며 고치는 화면 개선 (사용자 피드백)

로드맵 1~5단계 이후, 사용자가 직접 써 보고 낸 의견을 고친다. 항목은 의견이 올 때마다 늘어난다.

| 의견 | 고친 것 | 상태 |
|---|---|---|
| 한 문장(`a().b()->c()`)의 호출이 노드 보기에서 따로따로 보인다 | 같은 줄 묶음: 트리·노드 보기에서 "N줄" 상자 하나, 선도 하나(추정 연결은 묶지 않음) | ✅ |
| 코드에서 고른 줄이 진하기만 달라 구분이 안 된다 | 아래 칸으로 이어지는 줄은 파랑 + ▶ + 왼쪽 막대, 따라 들어간 호출 단추도 파랑 | ✅ |
| 세 칸 크기를 늘릴 수 없다 | 칸 경계선 끌기(좌우·위아래), 두 번 누르면 기본, 브라우저가 기억 | ✅ |
| "재분석", "편집기"가 무엇을 하는지 모르겠다 | "다시 분석"(툴팁에 대상), "코드 열기"(이 도구는 편집하지 않음) | ✅ |
| 대상 추가에서 돌아갈 수 없고, 보기 아이콘을 눌러도 안 바뀐다 | 왼쪽 위 이름 = 기본 화면, 보기 아이콘이 대상 추가를 닫음, "← 돌아가기" | ✅ |
| 편집기 열기를 눌러도 반응이 없다 | VS Code 확장 안에서 띄운 서버가 물려받은 ELECTRON_RUN_AS_NODE 등을 편집기 실행 때 뺌 | ✅ |
| 왼쪽 위 이름보다 홈 아이콘이 낫다 | 집 아이콘 + "홈" | ✅ |
| 묶음 상자를 눌러도 선택되지 않고, 안쪽 노드로 이동할 필요는 없다 | 묶음 상자·안쪽 노드를 누르면 그 줄 선택(코드 칸에서 그 줄 + 호출 단추, 묶음과 들어오는 선 파랑). 트리 묶음 머리도 같음 | ✅ |
| 노드를 옮기면 순서가 얽히고 자식이 따라오지 않아 소속을 모른다 | 노드를 끌면 트리 자식·손자도 같이, 선마다 호출 줄 번호, 화면 맞춤 = 처음 배치로 | ✅ |
| 단독 호출(AssertDirection)은 줄 번호가 없다 | 위와 같이 모든 선에 줄 번호 | ✅ |
| 묶음 안 노드는 움직이지 않게, 왼쪽 정렬로 | 묶음 안 함수는 왼쪽 끝 맞춤 + 고정(묶음은 상자를 잡고 통째로) | ✅ |
| 묶음 안 노드가 너무 붙어 있다 | 묶음 안 줄 간격 34 → 42(노드 사이 틈) | ✅ |

Codex·Claude 가 각각 낸 후보 중 묶음 A·B 를 진행한다. C(설정 규칙 시험 화면)는 써 본 뒤 결정.

| 묶음 | 기능 | 내용 | 상태 |
|---|---|---|---|
| A | ⑪ 문법 색칠 | 코드 스택의 C++·C# 키워드·문자열·주석·숫자·전처리 색. 여러 줄 주석·원시/축자 문자열 이어받기(Core `CodeColor`) | ✅ |
| A | ⑫ 함수 검색 | 검색칸에 함수 이름 → 닿는 진입점 목록(영향) + 진입점부터 그 함수까지 경로 | ✅ |
| A | ③ 뒤로/앞으로 | 보던 진입점·경로 기록(Alt+←/→, 마우스 단추), 새로 고침 뒤 마지막 위치 복원(새 결과에서 이어지는 데까지) | ✅ |
| B | ① 흐름 안 전후 비교 | 비교 기준이 있으면 코드 칸에서 바뀐 줄(빨강/초록), 지워진 함수도 기준 코드로 | ✅ |
| B | ② 검토 목록 | 함수마다 확인/보류/메모, 진입점별 진행률, 본문이 바뀌면 다시 봐야 함(`data/<대상>/review.json`). MCP `get_review` | ✅ |
| B | ④ git 변경 대조 | 작업 폴더 vs HEAD 의 바뀐 줄이 어느 흐름·함수에 걸리는지, 어떤 흐름에도 안 걸린 변경(읽기 명령만, `--no-optional-locks`) | ✅ |
